aic 对比 aicommits

aicommits 是 AI 提交信息工具里根深蒂固的默认选择——装机量、生态、先发优势都在它那边。本页无意粉饰这一点。它要准确告诉你 aic 何时更值得选——以及你何时就该继续用 aicommits。

巧了。aicommits 自己的 README 就建议，如果名字太长，可以把它别名成 aic。我们把 aic 作为独立的东西发布了——而且它在 hunk 层级把你的未暂存改动拆成多个逻辑提交，所以哪怕一个文件也能变成好几个。

aic 领先的地方

  • 把未暂存改动自动批处理成多个提交 aic 的招牌功能。aicommits 的 `--generate N` 是为一次提交生成 N 条候选信息，而不是 N 个提交。
  • 把单个文件跨多个提交拆分（按 hunk） 随 aic v0.3.5 发布。aicommits（以及 roundup 里的每个工具）最多只在文件边界拆分；aic 在 hunk 层级读 diff，所以一个文件涉及三件事就会变成三个聚焦的提交。
  • 解决合并冲突 aic 的第二个招牌流程（`v0.3.0`）。aicommits 没有任何冲突解决方案——它只在你手动合并完之后写那条信息。
  • 一等支持 Anthropic · Gemini · DeepSeek aicommits 只能间接到达这些模型；aic 把它们作为一等供应商发布，并配有合理的默认模型。
  • 运行时与依赖 aic 是一个静态可执行文件——没有 `node_modules`、传递依赖树，也不会在你切换 Node 版本时弄坏全局安装。（Rust 更快的冷启动也有帮助，尽管无论哪种情况 LLM 调用都是耗时大头。）只有当 Node.js 已经在你路径里时，aicommits 才称得上无摩擦。
  • 供应商覆盖 两者都能通过 OpenRouter 到达任意模型，但 aic 现在发布的一等供应商更多——包括 xAI、Together、Perplexity、Mistral——外加一个面向 LM Studio、vLLM 和网关的 OpenAI 兼容逃生通道。

aicommits 仍然占优的地方

我们不会假装 aic 在所有方面都胜过这个流行工具。它没有。如果下面这些对你来说比自动批处理更重要，那 aicommits 就是更对的选择：

  • 提交信息格式 aic 出于设计只支持约定式；aicommits 让你自选，包括一种无结构的普通模式。
  • Git 钩子集成 aicommits 通过一个钩子接入你常规的 `git commit` 流程；aic 则是显式运行。
  • 多个提交信息候选 aicommits 可以在提交前提供多条信息供你挑选。
  • 提示词与语言控制 aicommits 提供的可调项更丰富。aic 支持 `AIC_SYSTEM_PROMPT` 覆盖，但界面选项更少。
  • 人气与生态 aicommits 是那个知名度更高、社区更大的已知量。如果势头对你最重要，就继续用它。

常见问题

aic 是 aicommits 的好替代方案吗？

如果你想把未暂存的改动拆成逻辑提交——甚至在一个文件内——并希望 AI 解决合并冲突，那么是的。如果你依赖 git 钩子、gitmoji 提交或多条候选消息，aicommits 仍然是合适的选择。

aic 像 aicommits 一样需要 Node.js 吗？

不需要。aic 是单个 Rust 二进制——没有 node_modules、没有 npm 全局安装、没有 Node 版本兼容问题。
